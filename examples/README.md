# Example output

> ⚠️ **Everything in this directory is synthetic.**
> The project name (`demo-agent`), the files, the line numbers and the code are all
> **invented** to illustrate the *shape* of the output. Nothing here refers to a real
> repository, and no real finding is disclosed.

These files are generated by the pipeline, in this order:

| File | Produced by | What it is |
|---|---|---|
| [`param_taint_probe.md`](param_taint_probe.md) | `tools/param_taint_criteria.py` | per-candidate verdict on *controllability* (stage ② and ③) |
| [`findings.tsv`](findings.tsv) | `app/run_round.py` | the raw candidate table (22 columns) |
| [`report_draft.md`](report_draft.md) | `app/make_report.py` | the human-facing draft |
| [`agentaudit.sarif`](agentaudit.sarif) | `tools/to_sarif.py` | the same candidates as SARIF 2.1.0, for a code-scanning UI |

Every scan also writes an `index.html` (a sortable table) and `results.sarif` (the CodeQL
frontend's own raw output, full mode only); neither is included here because they are large
and add nothing to the picture.

---

## Reading order

1. **`param_taint_probe.md`** — the cheapest stage. It drops candidates that
   *cannot* be reached with an attacker-controlled value **before** spending any
   LLM credits. In the sample, 3 of 5 candidates are eliminated here for free.
2. **`findings.tsv`** — one row per surviving candidate. The interesting columns are
   `ai_verdict`, `by_design` / `scope_exceeds` (is it a designed feature, and does it
   exceed its intended scope?) and `arg_source` (where does the dangerous value come from?).
3. **`report_draft.md`** — only `vuln` rows, written up for a human. Note the header:
   it states plainly that this is **AI-assisted and not verified by execution**.
4. **`agentaudit.sarif`** — the same candidates in the format a code-scanning UI or an editor
   reads. Look at a `result`: the level is always `warning` (a candidate is not a confirmed
   vulnerability) and the triage verdict travels in `properties`. Paths are relative, so the
   file carries no filesystem layout.

---

## What the sample is trying to show

`demo-agent` is a fictional agent that exposes tools to an LLM. The four rows cover the
four outcomes the scanner is designed to distinguish:

| # | Sink | Verdict | Why |
|---|---|---|---|
| 1 | `subprocess.run` | **`vuln`** | argument is an LLM-supplied tool argument, reaches the sink unmodified |
| 2 | `eval` | `not_vuln` | argument is **locally enumerated**, not externally controllable |
| 3 | `open` | `not_vuln` | a validator on the path **normalises and constrains** the value |
| 4 | `open` | **`needs_human`** | the argument's origin **cannot be determined** from the available code |

★ Row 4 is the point. A scanner that only ever outputs `vuln` / `not_vuln` is lying
about its own certainty. `needs_human` is a **first-class result** here.
